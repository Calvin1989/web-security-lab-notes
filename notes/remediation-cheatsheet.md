\# Web 漏洞修复建议速查表



\## 1. SQL 注入



\### 漏洞根因



服务端将用户输入直接拼接到 SQL 语句中，导致用户输入改变了原本的查询逻辑。



\### 修复建议



\- 使用参数化查询或预编译语句；

\- 不要直接拼接 SQL 字符串；

\- 对输入参数进行类型校验，例如 ID 参数只允许数字；

\- 关闭详细数据库错误回显；

\- 数据库账号使用最小权限；

\- 对异常 SQL 报错和高危查询行为记录日志并告警。



\### 面试表达



SQL 注入的防御核心是参数化查询，而不是只依赖前端校验或黑名单过滤。

\## 2. XSS



\### 漏洞根因



服务端或前端将用户输入直接输出到页面中，未进行安全编码，导致浏览器将恶意脚本当作代码执行。



\### 修复建议



\- 对输出到 HTML 页面中的内容进行 HTML 实体编码；

\- 对输出到 JavaScript、URL、HTML 属性等不同上下文的数据使用对应编码方式；

\- 对输入进行必要的格式校验；

\- 设置 HttpOnly Cookie，降低 Cookie 被脚本读取的风险；

\- 配置 Content Security Policy；

\- 避免使用危险 DOM API，例如直接使用 `innerHTML` 拼接用户输入。



\### 面试表达



XSS 的防御重点是输出编码，要根据不同输出上下文选择不同编码方式。



\---



\## 3. 文件上传漏洞



\### 漏洞根因



服务端没有严格校验上传文件的类型、内容和存储位置，导致非预期文件被上传并可能被执行。



\### 修复建议



\- 使用文件类型白名单，只允许业务需要的文件类型；

\- 校验文件后缀、MIME 类型和文件真实内容；

\- 上传文件统一重命名，避免用户控制最终文件名；

\- 上传目录禁止执行脚本；

\- 上传文件存储到 Web 根目录之外；

\- 限制文件大小；

\- 对上传文件进行安全扫描；

\- 对上传行为记录日志并告警。



\### 面试表达



文件上传漏洞的关键风险是上传目录如果允许脚本执行，攻击者上传的脚本文件可能被服务器解析执行。



\---



\## 4. 命令执行漏洞



\### 漏洞根因



服务端将用户输入直接拼接到系统命令中执行，导致用户可以通过命令连接符执行额外系统命令。



\### 修复建议



\- 尽量避免直接调用系统 Shell；

\- 优先使用语言内置安全 API；

\- 对输入参数进行严格白名单校验；

\- 禁止命令连接符，例如 `\&`、`\&\&`、`|`、`;`；

\- 使用参数数组方式传参，避免字符串拼接命令；

\- Web 服务进程使用低权限账号运行；

\- 关闭详细错误回显；

\- 对异常命令执行行为记录日志并告警。



\### 面试表达



命令执行漏洞的防御重点是避免拼接系统命令，并对用户输入做严格白名单校验。



\---



\## 5. 目录遍历 / 任意文件读取



\### 漏洞根因



服务端根据用户传入的文件路径读取文件，但没有限制路径范围，导致用户可以通过 `../` 跳出指定目录。



\### 修复建议



\- 不直接使用用户传入的文件路径；

\- 使用文件 ID 映射真实文件路径；

\- 设置可读取文件白名单；

\- 对路径进行规范化处理；

\- 拦截 `../` 等目录跳转字符；

\- 限制文件读取根目录；

\- Web 服务账号使用最小权限；

\- 避免错误信息暴露真实服务器路径。



\### 面试表达



目录遍历的核心问题是服务端没有限制文件读取范围，不能只看文件是否存在，还要判断是否允许当前用户读取。

\## 6. 弱口令 / 暴力破解



\### 漏洞根因



系统存在简单密码或默认密码，并且登录接口没有失败次数限制、验证码、锁定或限速机制。



\### 修复建议



\- 禁止默认密码，首次登录强制修改；

\- 使用强密码策略；

\- 检测常见弱密码字典；

\- 限制连续登录失败次数；

\- 对同一账号或同一 IP 增加登录限速；

\- 必要时加入验证码；

\- 管理员账号启用多因素认证；

\- 记录登录成功、失败、来源 IP、User-Agent 和时间；

\- 对异常登录行为配置告警。



\### 面试表达



弱口令和暴力破解的风险不只是密码简单，还包括系统允许攻击者反复尝试。



\---



\## 7. 越权漏洞



\### 漏洞根因



服务端没有基于当前登录用户身份进行资源级权限校验，导致用户可以访问或操作不属于自己的数据。



\### 修复建议



\- 权限校验必须在服务端完成；

\- 不依赖前端隐藏按钮或菜单；

\- 查询用户资源时，从 Session 或 Token 获取当前用户身份；

\- 对订单、文件、地址、工单等资源做归属校验；

\- 管理员接口单独校验管理员权限；

\- 对越权访问、ID 枚举等异常行为记录日志；

\- 接口返回时避免暴露不必要的敏感字段。



\### 面试表达



越权漏洞的核心不是参数能不能改，而是服务端有没有判断当前用户是否有权访问该资源。



\---



\## 8. SSRF



\### 漏洞根因



服务端根据用户传入的 URL 发起请求，但没有限制目标地址、协议、IP 范围和重定向结果。



\### 修复建议



\- 对 URL 做白名单限制；

\- 限制协议为 `http` 和 `https`；

\- 禁止访问 `127.0.0.1`、`localhost`、`0.0.0.0`；

\- 禁止访问内网 IP 地址段；

\- 云环境中禁止访问云元数据地址；

\- 对 DNS 解析后的真实 IP 进行校验；

\- 禁止或严格校验重定向；

\- 设置请求超时和响应大小限制；

\- 对异常 URL 请求记录日志并告警。



\### 面试表达



SSRF 的本质是用户控制了服务器要访问哪里，服务器没有检查这个地址是否安全。



\---



\## 总结



常见 Web 漏洞的修复不能只依赖前端限制，应重点在服务端完成输入校验、输出编码、权限校验、安全配置和日志告警。



安全修复应遵循以下原则：



\- 输入不可信；

\- 输出要编码；

\- 权限在服务端校验；

\- 文件和路径要限制范围；

\- 系统命令避免拼接；

\- 数据库查询使用参数化；

\- 账号权限最小化；

\- 关键行为记录日志并告警。
