# 越权漏洞验证报告

## 1. 漏洞概述

本次测试针对用户资源访问接口进行越权验证，重点检查登录用户是否可以通过修改请求中的用户标识、资源 ID 或业务参数访问其他用户的数据。

测试发现，在权限校验不足的情况下，普通用户可能通过替换参数值查看其他用户信息，属于典型的水平越权风险，也可称为 IDOR（Insecure Direct Object Reference，不安全直接对象引用）问题。

## 2. 测试环境

- 靶场环境：Pikachu / 本地授权测试环境
- 测试账号：普通用户 A、普通用户 B
- 测试工具：Burp Suite、浏览器
- 测试时间：2026 年 6 月
- 测试范围：授权靶场中的 Over Permission 模块

## 3. 测试位置

- 请求方法：GET
- 测试路径：`/pikachu/vul/overpermission/op1/op1_mem.php`
- 测试参数：`username` / `user_id`
- 是否需要登录：是
- Cookie 是否参与验证：是，需携带当前登录用户 Cookie

示例请求位置：

```http
GET /pikachu/vul/overpermission/op1/op1_mem.php?username=lucy&submit=查看 HTTP/1.1
Host: 127.0.0.1
Cookie: PHPSESSID=***
```

## 4. 验证过程

### 4.1 Burp 抓包分析

使用普通用户 A 登录系统，进入个人信息或用户资料查看页面，点击查看自己的资料，并通过 Burp Suite 抓取请求。

抓包后发现，请求中存在用户标识参数，例如：

```text
username=lucy
```

该参数用于指定要查询的用户资料，因此属于越权测试重点参数。

截图：

![水平越权参数替换截图](../screenshots/access-control/04-horizontal-change-userid.png)

![水平越权 Burp 请求截图](../screenshots/access-control/06-burp-horizontal-request.png)

### 4.2 参数替换验证

在保持用户 A 登录态 Cookie 不变的情况下，将请求中的用户标识参数替换为用户 B 的标识。

示例：

```text
username=lucy
username=lili
```

测试逻辑：

1. 当前 Cookie 仍属于用户 A；
2. 只修改请求参数中的资源归属标识；
3. 观察服务端是否返回用户 B 的数据；
4. 判断服务端是否做了资源级权限校验。

如果替换参数后返回了用户 B 的资料，说明服务端仅根据前端传入参数查询数据，没有校验当前登录用户是否有权访问该资源。

### 4.3 响应差异对比

分别记录用户 A 正常访问和替换为用户 B 后的响应内容，对比返回数据中的姓名、手机号、邮箱、地址等字段。

截图：

![用户 A 信息页面截图](../screenshots/access-control/03-horizontal-user-a-info.png)

![替换参数后访问用户 B 信息截图](../screenshots/access-control/05-horizontal-user-b-info.png)

对比结论：

- 用户 A 正常请求时，响应返回用户 A 的资料；
- 保持用户 A Cookie 不变，仅替换 `username` 参数后，响应返回用户 B 的资料；
- 服务端未拒绝访问，也未返回权限不足提示。

由此可以判断该接口存在水平越权风险。

### 4.4 复测与补充验证

为避免误判，需要继续验证以下内容：

1. 是否只有当前模块存在问题，还是多个资源接口都可越权；
2. 是否能访问、修改或删除其他用户资源；
3. 是否可通过数字型 ID 递增枚举更多用户；
4. 服务端是否只在前端隐藏入口，而没有在后端做权限控制；
5. 修复后相同参数替换是否返回权限不足。

## 5. 风险影响

越权漏洞可能导致普通用户访问其他用户的个人资料、订单、地址、文件、消息、工单等敏感数据。如果接口还支持修改或删除操作，风险会进一步扩大，可能造成数据篡改、业务越权操作和隐私合规问题。

该类漏洞非常贴近真实业务测试，通常不是依靠工具扫描发现，而是依赖测试人员理解业务流程、用户角色和资源归属关系。

## 6. 修复建议

- 服务端必须基于当前登录用户身份进行权限校验，不可信任前端传入的用户标识；
- 查询用户资源时，应使用服务端会话中的用户 ID 作为权限判断依据；
- 对订单、文件、工单、地址等资源统一校验资源归属关系；
- 高权限接口应区分普通用户、管理员和运营角色；
- 避免使用可枚举的连续 ID 暴露敏感资源；
- 对越权访问、批量遍历、频繁 403/404 请求增加日志监控和告警；
- 修复后对同类接口进行横向排查，避免只修复单个接口。

## 7. 复测结论

修复后，保持用户 A Cookie 不变并再次替换为用户 B 的资源标识，服务端返回权限不足或空结果，不再返回其他用户数据。

复测结论：该越权风险已完成修复，当前未发现可继续通过参数替换访问其他用户资源的情况。
