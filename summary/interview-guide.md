\# Web Security Lab Notes 面试讲解稿



\## 1. 一句话介绍项目



这是一个基于 DVWA、Pikachu 本地授权靶场完成的 Web 安全漏洞复现与安全评估实践项目。



项目覆盖 SQL 注入、XSS、文件上传、命令执行、目录遍历、弱口令、水平越权、SSRF、CSRF、XXE、PHP 反序列化等 11 类常见 Web 漏洞，并结合 Burp Suite、Nmap、dirsearch、SQLmap、Nuclei 和 Python 日志分析脚本，完成漏洞复现、抓包分析、工具辅助验证、修复建议和安全运营日志研判。



\## 2. 1 分钟介绍版本



我做了一个 Web 安全漏洞复现与安全评估项目，主要基于 DVWA 和 Pikachu 本地授权靶场。



项目里我复现了 11 类常见 Web 漏洞，包括 SQL 注入、XSS、文件上传、命令执行、目录遍历、弱口令、越权、SSRF、CSRF、XXE 和 PHP 反序列化。每个漏洞都整理了复现步骤、Burp 抓包证据、风险影响、修复建议和复测思路。



后面我又补充了工具辅助安全评估流程，用 Nmap 做本地服务识别，用 dirsearch 做目录枚举，用 SQLmap 对已经手工确认的 SQL 注入点做辅助验证，用 Nuclei 做基础模板扫描和结果复核。



同时我还写了一个 Python access log 风险摘要脚本，把漏洞复现中的攻击特征转化成日志检测思路。这个项目重点不是单纯跑工具，而是体现从漏洞验证到风险分析、修复建议和安全运营研判的完整流程。



\## 3. 3 分钟介绍版本



这个项目是我为了系统学习 Web 安全和安全服务交付流程做的一个实践项目。



首先，我在本地搭建了 Windows、小皮面板、DVWA 和 Pikachu 环境，所有测试都限定在本地授权靶场中完成。项目覆盖了 11 类常见 Web 漏洞，包括 SQL 注入、XSS、文件上传、命令执行、目录遍历、弱口令、水平越权、SSRF、CSRF、XXE 和 PHP 反序列化。



在漏洞复现部分，我主要使用 Burp Suite 进行抓包分析。比如 SQL 注入中，我先用单引号观察 SQL 报错，再用永真条件验证查询逻辑被改变，最后通过 Burp 分析 id 参数如何被提交到后端。XSS 中，我分别复现了反射型和存储型 XSS，并对比了 Low 和 Impossible 模式下的差异。文件上传、命令执行、目录遍历等漏洞也都保留了页面结果和 Burp 请求证据。



第二部分是工具辅助安全评估。我使用 Kali 对 Windows 靶场进行辅助测试。Nmap 用于确认本地靶场的 Web 服务端口、MySQL 端口和 HTTP 指纹；dirsearch 用于目录枚举，识别 login.php、setup.php、README.md、.dockerignore、hackable/uploads 等路径，并进行人工复核；SQLmap 只用于对已经手工确认的 SQL 注入点做辅助验证，确认 id 参数存在注入，并识别出 MySQL 和当前数据库 dvwa；Nuclei 用于基础模板扫描，发现 DVWA 默认口令和 Dockerfile 文件暴露，并做人工复核。



第三部分是日志分析。我整理了常见 Web 攻击的日志特征和告警建议，并写了一个 Python 脚本 access-log-risk-summary.py，可以读取 access.log，识别 SQL 注入、XSS、目录遍历、命令执行、SSRF、XXE、PHP 反序列化等特征，生成 Markdown 风险摘要。



这个项目的核心思路是：手工验证是核心，工具用于信息收集、辅助验证和结果复核，最终风险判断需要结合业务场景、请求证据、响应结果和修复建议。

\## 5. 面试高频追问回答



\### 5.1 你这个项目是不是只是刷 DVWA？



不是。我确实使用了 DVWA 和 Pikachu 作为本地授权靶场，但项目重点不是刷题，而是把漏洞验证过程整理成接近安全服务交付的材料。



每个漏洞都有复现证据、Burp 请求分析、风险影响、修复建议和复测思路。后面还补充了 Nmap、dirsearch、SQLmap、Nuclei 的工具辅助评估流程，以及日志检测和安全运营分析思路。



\### 5.2 你怎么理解手工验证和工具扫描的关系？



我的理解是手工验证是核心，工具是辅助。



工具可以帮助做资产识别、目录枚举、已知模板扫描和辅助验证，但工具结果不能直接等同于漏洞结论。最终还需要人工结合请求参数、响应内容、业务逻辑、权限关系和修复建议进行判断。



比如 SQLmap 只用于对我已经手工确认的 SQL 注入点做辅助验证，而不是直接拿工具结果当最终结论。



\### 5.3 SQL 注入你是怎么验证的？



我先在 DVWA SQL Injection 模块中输入正常 ID，确认正常业务逻辑。然后输入单引号观察是否出现 SQL 报错，说明用户输入影响了 SQL 语句。接着输入永真条件，让页面返回多条用户记录，证明查询逻辑被改变。



之后我用 Burp Suite 抓包，确认 payload 是通过 id 参数提交的。最后使用 SQLmap 对这个已经手工确认的注入点进行辅助验证，SQLmap 识别出 id 参数存在注入，并识别出 MySQL 和当前数据库 dvwa。



\### 5.4 XSS 你怎么区分反射型和存储型？



反射型 XSS 的 payload 通常来自 URL 或请求参数，服务端马上把输入返回到页面，用户访问一次触发一次。



存储型 XSS 的 payload 会被保存到数据库或后端存储中，其他用户后续访问页面时也会触发。



我在 DVWA 中分别复现了反射型和存储型 XSS。存储型 XSS 中，脚本提交到留言板后刷新页面仍然触发，说明 payload 被保存了。



\### 5.5 文件上传漏洞你关注哪些防护点？



主要关注文件后缀、MIME 类型、文件内容、文件名重命名、上传目录权限和是否允许脚本执行。



安全修复上，应该使用白名单限制文件类型，对文件内容做校验，上传后重命名，上传目录禁止执行脚本，并尽量将上传文件存储在 Web 根目录之外。



\### 5.6 越权漏洞为什么工具不容易扫出来？



因为越权漏洞通常依赖业务身份和资源归属关系。工具可以发现路径，但很难理解“当前用户是否有权访问这个资源”。



比如水平越权需要登录用户 A 后修改参数访问用户 B 的信息，然后判断服务端是否做了资源归属校验。这类问题必须结合登录态、业务流程和人工判断。



\### 5.7 Nmap 在项目里起什么作用？



Nmap 在项目中不是用来证明漏洞，而是用于本地授权靶场的资产识别和服务枚举。



我用它确认 Windows 靶场主机开放了 80 端口和 3306 端口，识别 Web 服务和 MySQL 服务，并配合 http-title、http-server-header 脚本确认 HTTP 指纹，为后续 Web 测试确定资产范围。



\### 5.8 dirsearch 的结果能直接算漏洞吗？



不能。dirsearch 的结果只是路径发现线索。



比如发现 setup.php、README.md、.dockerignore、hackable/uploads 等路径后，还需要人工确认这些路径是否需要认证、是否泄露敏感信息、是否允许目录索引、是否能和文件上传或目录遍历等问题形成组合风险。



\### 5.9 SQLmap 为什么只做 current-db？



因为这是本地授权靶场中的辅助验证，我的目标是理解工具如何确认注入点和识别数据库信息，不是做数据导出。



真实安全评估中也应该遵守授权边界，不做未授权数据枚举、导出或破坏性操作。



\### 5.10 Nuclei 扫描结果怎么处理？



Nuclei 适合做自动化模板扫描和初筛，但结果需要人工复核。



这次 Nuclei 命中了 DVWA 默认账号口令和 Dockerfile 文件暴露。我结合前期弱口令手工验证确认默认账号风险，又用 curl 复核 Dockerfile 是否可访问。



对于 CSRF、越权、反序列化这类业务逻辑或请求体相关漏洞，Nuclei 不一定能覆盖，仍然需要手工验证。

\## 7. 面试时不要这样说



不要说：我熟练使用各种渗透测试工具。



更稳的说法是：我了解 Nmap、dirsearch、SQLmap、Nuclei 在授权测试中的基础使用方式，能完成资产识别、目录枚举、辅助验证和结果复核，但最终漏洞判断仍然以手工验证和业务分析为主。



不要说：我用 SQLmap 跑出了数据库。



更稳的说法是：我先手工确认 SQL 注入点，再用 SQLmap 对本地靶场注入点做辅助验证，仅确认注入类型和当前数据库名，没有做敏感数据导出。



不要说：Nuclei 可以自动发现所有漏洞。



更稳的说法是：Nuclei 适合做模板化问题初筛，但业务逻辑、越权、CSRF、反序列化等问题仍然需要结合登录态和业务流程手工验证。
